# ファイル監視機構の構造的課題と改善案

## 1. はじめに
`bugsList`取得時および監視時のリソース消費問題を受け、現在のファイル監視アーキテクチャを調査しました。結論として、デバウンス処理は症状の緩和としては有効ですが、根本的には**監視対象パスの動的管理に伴う複雑性と信頼性の欠如**という構造的課題が存在します。

## 2. 現状のアーキテクチャ
現在、`BugsWatcherService` および `SpecsWatcherService` は以下の方式を採用しています。
*   **個別パス監視方式**: プロジェクトルート全体ではなく、`.kiro/bugs/` や個別のWorktree内パスを計算し、`chokidar.watch()` にリストとして渡す。
*   **2層監視（2-tier monitoring）**: Worktree用ディレクトリ（`.kiro/worktrees/bugs/`）を監視し、新しいWorktreeが追加されたら、その内部の深いディレクトリパスを再計算して `watcher.add()` で動的に監視対象に加える。

## 3. 特定された構造的課題

### ① 監視状態の不透明性と二重監視のリスク
`chokidar` インスタンスに対して `add` や `unwatch` を動的に呼び出していますが、「現在どのパスを監視中か」を管理する状態（Set等）がサービス側に存在しません。
*   Worktreeの追加・削除が短時間に発生した場合、同じパスに対して重複して `add` が呼ばれる可能性があり、OSのファイルハンドルを無駄に消費するリスクがあります。
*   `unwatch` の漏れが発生しても検知する術がありません。

### ② タイミング依存の脆弱性（Race Condition）
Worktreeが作成される際、ディレクトリ構造（`.kiro/bugs/...`）が完成する前に監視を開始しようとするため、`setTimeout`（500ms）で待機するという不安定な実装になっています。
*   ファイルシステムの書き込み速度やOSの負荷によっては、500msでは不十分で監視に失敗したり、逆に早すぎたりする可能性があります。

### ③ イベント処理のオーバーヘッド
ファイル変更イベントが発生するたびに、パス解析（`extractBugName`）を実行しています。Worktreeの構造が深いため、監視対象ファイルが増えるほどCPUコストが増大する懸念があります。

## 4. 改善案

### 短期：監視状態の明示的・安全な管理
*   **`watchedPaths` Set の導入**: サービス内に現在監視中の全パスを保持するSetを追加し、`add`/`unwatch` 前に必ずチェックを行うことで二重監視とリソースリークを防ぎます。
*   **クリーンアップの保証**: `stop()` 時に全パスを確実に解除します。

### 中長期：ルート監視 + パターンフィルタリングへの移行
*   **広域監視への転換**: 個別のフォルダを `add` するのではなく、`.kiro` ディレクトリ全体を1つのウォッチャーで監視します。
*   **Globパターンによる抽出**: `chokidar` の機能や高速なGlobマッチングを使用し、関心のあるパスのみを抽出するようにリファクタリングします。これにより動的なパス追加ロジック自体を排除します。
