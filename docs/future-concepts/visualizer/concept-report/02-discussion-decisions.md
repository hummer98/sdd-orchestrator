# 2. 議論による決定内容と理由

## 議論の経緯

### 質問1: 対象範囲について

**質問**: すべてのsteeringファイルを統合した「プロジェクト全体像」を1つの可視化にするのか？各steeringを別々に可視化するのか？

**ユーザー回答**: 「どう思いますか？統合すべき？」→ 判断を委ねられた

**決定**:
- **両方のアプローチを採用**
- `steering_overview.html`: 全体統合ビュー
- `architecture_diagram.html`, `state_flow.html`: 個別詳細ビュー

**理由**:
- 全体像の把握には統合ビューが必要
- 詳細理解には個別ビューが効果的
- ユースケースによって必要な粒度が異なる

### 質問2: 主なユースケースについて

**質問**: オンボーディング、継続的レビュー、その他のどれを優先するか？

**ユーザー回答**: 「どれもです」

**決定**: 全ユースケースをカバーする設計

| ユースケース | 対応する可視化 |
|-------------|---------------|
| オンボーディング | steering_overview, architecture_diagram |
| 設計レビュー | state_flow, process_boundary |
| 参照 | 全て（検索・フィルタ機能で対応） |

### 質問3: 可視化で最も重要な要素

**質問**: アーキテクチャ、ディレクトリ構造、状態管理、ワークフロー、技術スタックのどれを優先するか？

**ユーザー回答**: 「アーキテクチャ、状態管理、ワークフローなどですかね」

**追加コメント**: 「複雑かつ重要な処理についてはアニメータブルなシーケンス図といった認知の助けになりそうなものもあったほうがいい」

**決定**:
- アーキテクチャ図 → `architecture_diagram.html`
- 状態管理フロー → `state_flow.html`（アニメーション付き）
- ワークフロー → `workflow_diagram.html`（将来実装）
- ディレクトリ構造は `architecture_diagram.html` に含める

### 質問4: 判断の委譲

**ユーザーコメント**: 「何をビジュアライズすべきかは調査結果から判断してください」

**決定**: 調査結果に基づき以下を優先的に可視化

1. **Steering階層構造** - ファイル間関係の理解が最初のハードル
2. **アーキテクチャ** - Electron Main/Renderer/Remote UIの理解が必須
3. **状態管理フロー** - 頻出の設計判断でありアニメーションが効果的

## 決定事項サマリー

| 決定項目 | 内容 | 理由 |
|---------|------|------|
| 可視化タイプ | 5種類（overview, architecture, state_flow, workflow, process_boundary） | ユースケース網羅 |
| ライブラリ | Cytoscape.js | 物理演算、アニメーション、複合ノード対応 |
| 出力形式 | Single File HTML | ポータビリティ、既存visualization.md準拠 |
| アニメーション | state_flow.htmlに実装 | 複雑な処理の理解に効果的 |
| Progressive Disclosure | 採用 | 認知負荷軽減 |
| ダークモード | 必須 | 既存ガイドライン準拠 |

## 採用しなかった選択肢

| 選択肢 | 不採用理由 |
|--------|-----------|
| React/Vite統合 | SDDアーティファクトとしての独立性を優先 |
| Mermaid.js | インタラクティブ性・アニメーションが不足 |
| D3.js単体 | 学習コスト高、Cytoscape.jsで十分 |
| 静的画像生成 | インタラクティブ性が失われる |
| 全ての詳細を1つのビューに | 認知負荷が増大 |
