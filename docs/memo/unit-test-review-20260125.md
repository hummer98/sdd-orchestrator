# ユニットテストレビュー報告書 (2026-01-25)

## 概要
`electron-sdd-manager` プロジェクトのユニットテストを調査しました。
全体として、テストスイートは非常に堅牢で、321ファイル/6733テストが全てパスしており、カバレッジも高そうです。

## 調査結果詳細

### 1. 全体的な健全性
*   **状態**: 良好。全てのテストがパスしています。
*   **構造**: テストは機能ごとに適切に分離されており、ユニットテスト（モック多用）と統合テスト（実プロセス使用）のバランスが取れています。

### 2. 重複・過剰なテスト
*   **`specStore.test.ts` と `specDetailStore.test.ts` の重複**:
    *   `specStore.ts` は `specStoreFacade.ts` を含む各ストアの再エクスポート（Facade）ですが、`specStore.test.ts` 内の `selectSpec` や `refreshSpecDetail` などのテストケースは、`specDetailStore.test.ts` 内のロジックテストと重複しています。
    *   `specStore.test.ts` は Facade が正しく委譲しているかを確認する統合テストとしての役割を果たしていますが、ステートの詳細な遷移まで再検証している部分は冗長です。

### 3. モックと統合のバランス
*   **`specManagerService.test.ts`**:
    *   `electron` や `createAgentProcess` を重厚にモックしており、純粋なロジックフローのテストとして機能しています。
    *   「過剰なモック」に見える可能性がありますが、実際のプロセス生成を行う `agentProcess.test.ts` が別途存在し、そこで `echo` や `ls` コマンドを用いた実プロセス制御のテストが行われているため、全体として適切な階層構造になっています。

### 4. 些細または意味の薄いテスト
*   **`timeFormat.test.ts`**:
    *   非常に単純なフォーマット関数のテストですが、表示ロジックの回帰防止として必要十分であり、「無意味」ではありません。
*   **`handlers.test.ts`**:
    *   IPCハンドラーの登録を確認するテストが多く含まれています（`should register X handler`）。これらは実装詳細（特定の文字列で `ipcMain.handle` が呼ばれたか）を確認するものであり、ロジックそのものをテストしていませんが、オーケストレーターとしての責務を確認する上では許容範囲です。

### 5. カバレッジに関する考察
*   **不足の可能性**:
    *   `auto-impl` フェーズや、SSH接続失敗時の詳細なエラーハンドリングなど、エッジケースの一部はモックで済まされており、実環境での挙動（特にネットワークやファイルシステムのエラー）の検証は手動テストやE2Eテストに依存している部分があります。しかし、ユニットテストのスコープとしては適切です。

## 今後の改善提案 (Actionable Proposals)

### 1. `specStore.test.ts` のリファクタリング（重複排除）
*   **現状**: `specStore` は Facade パターンを採用していますが、テストコード内で下位ストア（`specDetailStore` など）のロジックまで重複して検証しています。
*   **提案**: `specStore.test.ts` のテスト範囲を「委譲（Delegation）が正しく行われているか」の確認に限定します。
    *   具体的には、ステートの変化そのものをアサートするのではなく、`specDetailStore` のメソッドが**期待される引数で呼び出されたか**をスパイ（Spy）やモックを用いて検証する形に変更します。
*   **効果**: ロジック重複の排除により、将来的な仕様変更時の修正コスト（各テストファイルの修正漏れリスク）を低減できます。

### 2. エラーハンドリングのテスト強化
*   **現状**: SSH接続エラーやファイルシステム書き込みエラーなど、物理的な外部要因による異常系の検証が一部 E2E や手動テストに依存しています。
*   **提案**: 特に `auto-impl` フェーズや SSH 接続周りにおいて、意図的に例外をスローするモックを使用したユニットテストケースを追加します。
    *   アプリケーションが未補足の例外でクラッシュせず、ユーザーに適切なエラーメッセージを表示するか、あるいは適切なエラー状態（Error State）に遷移するかを重点的に検証します。

### 3. IPC ハンドラーテストの効率化
*   **現状**: `handlers.test.ts` には `should register ...` という反復的な登録確認コードが多数存在します。
*   **提案**: IPC ハンドラーの登録を検証するためのカスタムマッチャーやヘルパー関数を導入することを検討してください。
    *   これによりテストコードの記述量を減らし、どのチャンネルにどのハンドラーが紐付いているかの定義一覧としての可読性を向上させます。

### 4. アーキテクチャ刷新の提案 (tRPC導入)
*   **現状**: `handlers.ts` が巨大化しており、IPCチャンネル名の文字列管理や手動バリデーション（`validateProjectCommandParams` 等）のテストに工数が割かれています。また、テストコード内で `ipcMain` や `BrowserWindow` のモック作成が不可欠となっています。
*   **提案**: **tRPC (TypeScript Remote Procedure Call)** の導入を強く推奨します。
    *   **型安全性**: フロントエンドとバックエンドで型定義を共有できるため、チャンネル名のタイプミスや引数の不整合がコンパイル時に検出可能になります。
    *   **テストの簡素化**: 「IPCチャンネルが正しく登録されているか」という配管のテストが不要になります。また、プロシージャを純粋な関数としてテストできるため、Electron固有の複雑なモック（`event.sender` 等）を排除できます。
    *   **バリデーション**: Zod 等のスキーマバリデーションにより、手動の入力チェックコードとそのテストケースを削除できます。
