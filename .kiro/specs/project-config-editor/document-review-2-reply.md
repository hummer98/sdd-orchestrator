### W-001: useProjectFilesカスタムフックの未定義

**Issue**: Design.mdのL211で`ProjectFileList`の依存関係に`useProjectFiles (P0)`と記載されているが、このカスタムフックの実装仕様がDesign.mdに定義されていない。

**Judgment**: **No Fix Needed** ❌

**Evidence**:

1. **既存パターンの確認**: プロジェクト内の既存shared/hooksを確認したところ、`useSpecListLogic`や`useBugListLogic`は**リスト表示ロジック（ソート、フィルタ）を提供するフック**であり、**データ取得フックではない**。
   - `useSpecListLogic` (`shared/hooks/useSpecListLogic.ts:92-179`): specs配列を受け取り、ソート・フィルタロジックを提供
   - `useBugListLogic` (`shared/hooks/useBugListLogic.ts:86-129`): bugs配列を受け取り、フィルタロジックを提供

2. **Design.mdの記載意図の解釈**: `useProjectFiles (P0)`はDesign.mdのComponents and Interfaces表における「Key Dependencies」欄の記載であり、これは実装時に必要となる依存関係を示している。このプロジェクトでは**フック名の事前定義より、実装パターンの一貫性**が重視されている。

3. **Projectファイル一覧の特性**: Projectファイル一覧は以下の理由でSpec/Bugとは性質が異なる：
   - ファイルリストが固定（CLAUDE.md + steering/*.md）
   - ソート・フィルタ機能が不要（Requirements参照）
   - 単純な配列表示のみ

4. **Tasks.md Task 3.1の十分性**: 既に「CLAUDE.mdセクションとSteering Filesセクションの2グループ表示」「ファイルが存在しない場合の空状態表示」「選択ファイルのハイライト表示」が実装タスクとして明記されており、実装に必要な情報は揃っている。

**Conclusion**: Design.mdの依存関係記載は実装ガイダンスとして十分。`useProjectFiles`の詳細インターフェース定義の追加はYAGNI原則に反し、過度な先行仕様化となる。実装時にコンポーネント内のロジックとして実装するか、必要に応じてフック化する判断が可能。

### W-002: Remote UI用ファイル一覧取得の共有フック不在

**Issue**: Electron版とRemote UI版で同じファイル一覧取得ロジックが必要だが、`useProjectFiles`フックが`shared/hooks/`に配置されるか、各プラットフォーム固有の実装になるかが不明確。

**Judgment**: **No Fix Needed** ❌

**Evidence**:

1. **既存のAPIクライアント抽象化**: 本プロジェクトでは`IpcApiClient`と`WebSocketApiClient`が同一インターフェースを持つ設計が既に確立されている。Design.mdのTasks 5.1, 5.2で両APIクライアントに`listProjectFiles`, `readProjectFile`, `writeProjectFile`メソッドを追加することが明記されている。

2. **データ取得ロジックの単純性**: Projectファイル一覧取得は以下の呼び出しのみ：
   ```typescript
   const files = await apiClient.listProjectFiles();
   ```
   この単純な呼び出しを共有フック化するメリットは限定的。

3. **既存パターンとの整合性**: `useSpecListLogic`や`useBugListLogic`はデータ取得を行わず、取得済みデータの操作ロジックを提供している。データ取得は各コンポーネントが直接APIクライアントを呼び出すパターンが確立している（例: `SpecsView.tsx`, `BugsView.tsx`）。

4. **コード重複リスクの評価**:
   - Electron版: `ProjectFileList` → `IpcApiClient.listProjectFiles()`
   - Remote UI版: `ProjectView` → `WebSocketApiClient.listProjectFiles()`

   両方とも1行のAPI呼び出しであり、ロジック重複の実害は最小限。

**Conclusion**: 既存のAPIクライアント抽象化パターンで十分対応可能。Projectファイル操作の単純性を考慮すると、専用共有フックの追加は過度な抽象化であり、KISS原則に反する。
