# e2eテストについてのスタンス

現在、electron-e2e, web-e2eなど、プロジェクトに応じたe2eテストケースを作るかどうかはsteeringドキュメントやプロンプト指示に左右される
部分があり、Spec/Bugなどの仕様書に記述されるか、tasksにe2eテスト項目が入るかはまちまちなところがある。(課題1)
また、実行基準についても、全体をテストするのか、作成したe2eテストだけでいいのか、関連する部分も含めた限定的なe2eテストでいいのかの判断基準も曖昧である(課題2)

そこで、以下のようにe2eテストを形式化して、ワークフローに組み込む事にする
ただし、phaseとして実行するというよりは、spec-inspectionの一貫として実行する事を検討している。

特に以下の観点で意見をください
- そもそもこの構想の妥当性について
- サブエージェントの責務分担について。分離or他のphaseに責務を追加したほうがいいか。あるいは既存のspec-*系コマンドから責務を剥がして新しいサブエージェントに任せたほうがいいか。
- e2e実行サブエージェント, e2e作成サブエージェントはプロジェクトによる差が大きい懸念がある、generate-*系コマンドのようにプロジェクト解析からエージェントプロンプトを作成する方法のほうがいいか、汎用プロンプトでなんとかなるかの検討。
- サブエージェントではなく、skills, slash commandsによる実装にするべきかの判断

## 想定しているサブエージェント

### e2e計画・作成サブエージェント
- spec-implとは違う観点で、仕様を確認するのに必要なe2eテストを考案、あるいは既存テストの改修を行う専門のサブエージェント

### e2e実行サブエージェント
- e2eの実行環境に関する知識を持ち、テスト実行時のトラブルなどを解決し、適切なe2eテストを実行し、結果を指定したフォルダにテンプレートに沿った内容で記述する。
- テストケース自体の修正は行わない。

## e2eテストの詳細についてのプロジェクト毎コンテキストの分離
e2eテストの詳細と達成すべき内容についてはサブエージェント自体には直接記述せず、steeringファイル内のinspection-e2e.md などに分離する。
sdd orchestratorとしてはこのinspection-e2e.mdを作成する generate-inspection-e2e.md というような生成用Slash Commandsを提供する。
このコマンドでプロジェクトの解析を行って、e2eテストの実行方法や環境、排他制御の必要性などを調査、検討、提案なども対話的に行う。
(他のgenerate-*系コマンドを参照)

## 実行スコープの決定
いずれかのspec-*、またはe2e計画・作成サブエージェントが、仕様および実装に応じて、e2eの実行範囲を決定し、不足があれば作成する。
実行自体はinspectionで行うべきか、implで(つまりtasksに追加して実行)すべきか要検討。

## e2eテスト内容についてのサマリードキュメントのメンテナンス
- steeringにe2eテスト内容についての詳細ドキュメントを用意する、どのファイルが何のテストを行っているのかがわかる資料となっていること
- このファイルはe2eテスト作成エージェント

## e2eテストレポートの統一
- .kiro/specs/<spec-name> に e2eテストの結果報告の作成を義務化する。inspectionのように、テスト毎にファイルを作成しインデックス番号を更新していくこと。
- これによりspec-inspectでの結果確認や、テスト-fixのサイクルがどのように行われたかの証跡となる


# inspection責務の肥大化

現在、spec-inspection.md、すなわちinspectionフェーズは仕様書適合性、実装妥当性、統合の妥当性など、多数の観点で行うため、責務が非常に拡大していて、各観点のチェックにコンテキストウィンドウ的な負荷がかかるため、ClaudeCodeの検査能力が劣後する場合がしばしばある。（特に項目数が多い仕様など）

そこで、一部の検査責務を複数のサブエージェントに分散することでそれぞれの観点での検査を実行し、spec-inspectionそのものはそれらのサブエージェントからの報告を受けて総合的に判断、レポートを作成する責務というように分担する。

前項のe2eに関してもこの観点の一つとしてinspection中にサブエージェントとして実行する構想である。

このアイデアについての意見を述べてください。
- 直近のinspection-1.mdなどのレポートを参照してみてください。
- そもそもこの構想の要/不用について、たとえばコンテキストウィンドウには余裕があるので意味がない、など
- どのようなサブエージェントに分散すべきか
- 分散することでサブエージェント間での情報共有が行われず、統合的なレポートに支障がでる可能性
