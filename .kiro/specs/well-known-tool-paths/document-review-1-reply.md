### W2: ロギング仕様が詳細化されていない

**Issue**: ツールパス解決成功/失敗時のログ出力仕様を追加すべき

**Judgment**: **No Fix Needed** ❌

**Evidence**:
1. 既存の`ToolPathResolverService`（`toolPathResolverService.ts:141-260`）では既に適切なロギングが実装されている：
   - `logger.info('[ToolPathResolver] Resolving all tools in parallel')`
   - `logger.info('[ToolPathResolver] Tool resolved successfully', { tool, path, version })`
   - `logger.warn('[ToolPathResolver] Failed to resolve tool', { tool, error })`
   - `logger.debug('[ToolPathResolver] Returning cached result', { tool, resolved, path })`

2. logging.md（`.kiro/steering/logging.md`）にログレベルの選択基準が定義されており、実装時にこれに従うのがプロジェクトの標準パターン

3. 他のサービス（`engineConfigService.ts`, `remoteAccessServer.ts`等）でも、design.mdにログ仕様を詳細化するパターンは採用されていない

4. design.mdの「Error Handling」セクションで「ログ出力」への言及は既にあり、実装時のガイダンスとしては十分

**Conclusion**: 既存パターンに従い、実装時にlogging.mdガイドラインを適用すれば十分。design.mdへの過度な詳細化はYAGNIの原則に反する。

### W3: 運用メトリクスの収集なし

**Issue**: ツールパス解決失敗の頻度を追跡する仕組みがない

**Judgment**: **No Fix Needed** ❌

**Evidence**:
1. **YAGNI原則**: 「将来のWell Knownパス追加検討のため」は仮定に基づく要件であり、現時点で必要性が証明されていない

2. **現在の設計意図**: この仕様の目的は「シェル起動による副作用を排除し、安定したパス解決を実現する」こと。メトリクス収集は別の関心事

3. **ログによる代替**: 解決失敗時には`logger.warn`でログ出力されるため、必要に応じてログ分析で傾向は把握可能

4. **スコープ管理**: Out of Scopeに明記された「ツールの自動インストール機能」「バージョン要件のチェック」と同様、メトリクス収集は将来の別仕様として検討すべき

**Conclusion**: 現時点では不要。将来の機能拡張として検討する場合は、別途spec-initで新規仕様を作成すべき。
